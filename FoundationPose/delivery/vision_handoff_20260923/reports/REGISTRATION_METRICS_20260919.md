# 注册、重注册、跟踪与真实运行显存验收

2026-09-19 已实现统一事件和汇总，并在本机 D435i + RTX 4070 的完整压缩 ROS2 → YOLO → FoundationPose → ObjectPose 流水线上完成两组测试。相机采集 1280×720，约 15 Hz 发布；目标类别 0、检测门限 0.30、YOLO 输入 960，FP 输入最长边 640；模型保持 φ65.1×159.5 mm，不改变位姿或选目标算法。

所有测试位姿只发布到 `/sb_metrics_test/object_pose`，没有机器人运动。模型与几何质量检查均使用真实后端，不使用合成姿态替代检测结果。全量搜索是测试脚本显式强制既有后备路径，生产默认搜索策略保持不变。

## 实机阶段耗时

以下是 register/track 实际调用时间 `pose_s`，不包含模型加载、YOLO 与结果质量检查；完整阶段数据保存在各组 `summary.json`。

| 运行组 | 操作 | 样本数 | P50 ms | P95 ms | 最大 ms |
|---|---|---:|---:|---:|---:|
| 配置搜索 | 首次注册 | 1 | 253.03 | 253.03 | 253.03 |
| 配置搜索 | 重注册 | 3 | 128.85 | 130.72 | 130.93 |
| 配置搜索 | 连续跟踪 | 613 | 19.51 | 26.63 | 40.55 |
| 全量搜索 | 首次注册 | 1 | 994.54 | 994.54 | 994.54 |
| 全量搜索 | 重注册 | 2 | 904.55 | 905.60 | 905.71 |
| 全量搜索 | 连续跟踪 | 488 | 24.93 | 34.73 | 48.20 |

配置搜索实际生成 48 个旋转候选，refine 12 个；全量搜索实际生成并 refine 240 个。事件记录 `force_full_requested`、`search_executed`、`full_search` 和实际候选数量，不只记录请求参数。

每组首次注册只有 1 个样本，P50/P95/最大值因此相同；重注册仅 3/2 个样本，其分位数是小样本描述，不是长期性能保证。本次恢复由私有节点的 reset 服务触发，模拟重新选目标，不等同于物理遮挡或移动场景的恢复分布。

## 首次输出与恢复

| 指标 | 配置搜索（50 秒运行） | 全量搜索（40 秒运行） |
|---|---:|---:|
| 首次模型加载 | 7.752 s | 3.630 s |
| 节点启动到首次有效发布 | 8.688 s | 5.798 s |
| reset 到首次有效发布 P50 | 265.15 ms | 983.76 ms |
| reset 到首次有效发布 P95 | 265.54 ms | 984.02 ms |
| reset 到首次有效发布最大 | 265.59 ms | 984.05 ms |
| 发布端实际发布/接收端收到的样本 | 613 | 487 |

冷启动包括模型加载、首次 CUDA 初始化/缓存状态、等待帧等；两次是不同进程运行，不能将全量组首发更快解释为全量算法更快。

配置组的首次注册估计有效，但该任务含模型加载，结果过期，因此没有直接发布；下一新帧跟踪后才完成首发。三次配置搜索重注册都通过了发布门控。
全量组的三次注册都计算出了通过几何检查的估计，但注册所用旧帧未通过时效/reset 边界门控，没有直接发布；随后新帧跟踪通过后恢复发布。事件中 `estimate_valid` 和 `published` 分别记录，恢复计时以真正调用发布结束为准。
全量组期间存在一帧无检测，但保留了模型加载统计。不会把无输出或未完成恢复写成 0 秒成功。

## 真实流水线显存

设备：NVIDIA GeForce RTX 4070，UUID `GPU-5e4f41ce-b951-06f0-0428-403c18cf793a`。

| 显存口径 | 配置搜索 | 全量搜索 |
|---|---:|---:|
| NVML 本进程采样峰值 | 1.428 GiB | 6.311 GiB |
| PyTorch 已分配峰值 | 0.776 GiB | 3.196 GiB |
| PyTorch 已保留峰值 | 0.939 GiB | 5.414 GiB |

NVML 每 50 ms 采样本 PID 的显存，分别采到 958/767 次，不包括其他进程的显存；可能漏掉间隔内的短暂尖峰。PyTorch 高水位从加载后端前开始、不在每次注册时重置，但不覆盖所有 CUDA/渲染器分配。因此三个数分别报告，没有互相替代，也没有引用合成 GPU 测试的峰值。
配置组订阅独立运行的真实相机进程；全量组的测量进程同时包含相机 ROS 发布节点。两者运行布局写入说明，不能把差异全部归因于搜索方式。

## 代码与协议

- `my_demo/sb_vision_pipeline.py`：明确 `initial_registration / reregistration / tracking`；记录事件号、注册尝试号、触发原因、搜索详情、阶段耗时和异常。
- `estimater.py`：只增加搜索实际执行信息，包含提前返回和候选数；没有修改候选选择或 refinement 算法。
- `my_demo/vision_metrics.py`：统一计数、P50/P95/最大值、输出恢复计时、NVML 采样及原子汇总。
- `my_demo/sb_vision_node.py`：记录 reset/时钟原因、真正发布时刻、模型加载、退出时在途任务；默认会话 JSONL、每秒及关闭时的 summary、ROS 状态中的 performance。
- `my_demo/scripts/benchmark_registration.py`：可复跑的真实相机测量脚本、私有话题、受控 reset 和可选全量补测。
- `my_demo/README_registration_metrics.md`：字段、计时、分位数窗口和显存口径。

首次注册定义为进程内第一次 register 尝试；失败后的重试也属于重注册，并有 `registration_quality_rejected` 原因。进程 UUID、注册尝试号与目标代次分别记录。原有 `operation=register/track` 和时间键保留兼容。
